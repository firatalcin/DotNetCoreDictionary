## SQL Temelleri

### S1. Primary key ve foreign key nedir? Aralarındaki ilişkiyi açıklayın.

**Primary Key (PK)**, bir tablodaki her satırı benzersiz biçimde tanımlayan kimlik kolonudur (veya kolon grubudur). Tekrar eden değer alamaz, `NULL` olamaz ve kayıt yaşam döngüsü boyunca değiştirilmemelidir; bu nedenle e-posta veya TC kimlik numarası gibi anlamlı veriler yerine genellikle `INT IDENTITY(1,1)` gibi sistemin ürettiği yapay bir anahtar tercih edilir.

**Foreign Key (FK)** ise bir tablodaki kolonun başka bir tablonun Primary Key'ine işaret ederek iki tablo arasında bağlantı kurmasıdır. Bu ilişki iki temel fayda sağlar: veriyi tek bir yerde tutarak veri tekrarını önler ve **referans bütünlüğünü (referential integrity)** korur. Yani ana tabloda karşılığı bulunmayan bir kimlikle kayıt eklenmesini veya bağlı kayıtları bulunan bir ana kaydın kontrolsüzce silinmesini veritabanı seviyesinde engeller.

**Örnek:**
```sql
CREATE TABLE Customers (
    CustomerId INT IDENTITY(1,1) PRIMARY KEY,
    FullName   NVARCHAR(100) NOT NULL
);

CREATE TABLE Orders (
    OrderId    INT IDENTITY(1,1) PRIMARY KEY,
    CustomerId INT NOT NULL,
    Total      DECIMAL(10, 2) NOT NULL,
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId)
);
-- Customers tablosunda CustomerId = 99 yoksa bu kayıt FK kısıtına takılır.
```

### S2. INNER JOIN ile LEFT JOIN arasındaki fark nedir?

`INNER JOIN`, iki tabloyu `ON` koşuluna göre eşleştirir ve yalnızca **her iki tabloda da karşılığı bulunan** satırların kesişimini döndürür. Eşleşmesi olmayan kayıtlar sonuç kümesine dahil edilmez.

`LEFT JOIN` (LEFT OUTER JOIN) ise soldaki tablonun **tüm satırlarını** korur ve sağdaki tablodan eşleşen kayıtları yanlarına getirir; sağ tabloda karşılığı olmayan satırların sağ tablo kolonlarını `NULL` ile doldurur. Bu sayede "hiç sipariş vermemiş müşteriler" veya "hiç ürünü olmayan kategoriler" gibi eşleşmeyen kayıtları bulmak (`anti-join`) yalnızca `LEFT JOIN` ile mümkündür.

**Örnek:**
```sql
-- INNER JOIN: Sadece en az bir siparişi olan müşteriler gelir.
SELECT c.FullName, o.OrderId
FROM Customers c
INNER JOIN Orders o ON o.CustomerId = c.CustomerId;

-- LEFT JOIN: Tüm müşteriler gelir; siparişi olmayanlarda o.OrderId NULL olur.
SELECT c.FullName
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.CustomerId
WHERE o.OrderId IS NULL; -- Hiç sipariş vermemiş müşteriler
```

### S3. WHERE ile HAVING arasındaki fark nedir?

Hem `WHERE` hem de `HAVING` filtreleme yapar; ancak SQL sorgusunun mantıksal çalışma sırasındaki yerleri farklıdır. `WHERE`, `GROUP BY` adımından **önce** çalışarak ham satırları tek tek eler; bu nedenle `WHERE` içinde `SUM`, `COUNT`, `AVG` gibi aggregate fonksiyonlar kullanılamaz.

`HAVING` ise `GROUP BY` adımından **sonra** çalışır ve oluşturulmuş grupları aggregate sonuçlarına göre filtreler. Satır bazlı koşulları `WHERE` içinde yazmak hem doğru mantık kurar hem de gruplamaya girecek satır sayısını baştan azaltarak performansı iyileştirir; toplam veya sayım koşulları ise `HAVING` ile yazılır.

**Örnek:**
```sql
SELECT CustomerId, SUM(Total) AS TotalSpent
FROM Orders
WHERE OrderDate >= '2026-01-01'      -- Önce satırları tarihe göre filtreler
GROUP BY CustomerId
HAVING SUM(Total) > 1000;            -- Sonra grupları toplam tutara göre filtreler
```

### S4. One-to-Many ilişkiyi örnekle açıklayın.

**One-to-Many (1-N)**, ilişkisel veritabanlarında en yaygın kullanılan ilişki türüdür. "Bir" tarafındaki (principal) tek bir kayıt, "çok" tarafındaki (dependent) sıfır, bir veya birden fazla kayıtla ilişkili olabilirken; "çok" tarafındaki her kayıt yalnızca tek bir ana kayda bağlıdır.

Veritabanı tasarımında Foreign Key her zaman **"çok" tarafındaki tabloya** yerleştirilir. Böylece ana tablo tekrarlanmaz ve her alt kayıt hangi üst kayda ait olduğunu kendi FK kolonuyla tutar. EF Core tarafında bu ilişki ana sınıfta koleksiyon (`ICollection<Product>`), alt sınıfta ise hem FK (`CategoryId`) hem de navigation property (`Category`) ile modellenir.

**Örnek:**
Bir kategorinin birden fazla ürünü olabilir, ancak her ürün yalnızca tek bir kategoriye aittir (`Categories` 1 — N `Products`).
```sql
CREATE TABLE Categories (
    CategoryId INT IDENTITY(1,1) PRIMARY KEY,
    Name       NVARCHAR(100) NOT NULL
);

CREATE TABLE Products (
    ProductId  INT IDENTITY(1,1) PRIMARY KEY,
    Name       NVARCHAR(150) NOT NULL,
    CategoryId INT NOT NULL CONSTRAINT FK_Products_Categories
        FOREIGN KEY REFERENCES Categories(CategoryId)
);
```

### S5. Normalizasyon nedir? Neden yapılır?

**Normalizasyon**, ilişkisel bir veritabanında veri tekrarını ortadan kaldırmak ve veri bütünlüğünü sağlamak için tabloları belirli kurallara (1NF, 2NF, 3NF) göre parçalama ve yapılandırma sürecidir. Kısaca 1NF her hücrede tek bir atomik değer bulunmasını, 2NF birleşik anahtarlı tablolarda her kolonun anahtarın tamamına bağlı olmasını, 3NF ise anahtar olmayan kolonların birbirine bağımlı olmamasını şart koşar.

Normalizasyon yapılmadığında **güncelleme, ekleme ve silme anomalileri** ortaya çıkar. Örneğin bir tedarikçinin telefon numarası her ürün satırında tekrar ediyorsa, telefon değiştiğinde yüzlerce satırı güncellemek gerekir ve bir satırın atlanması tutarsız veriye yol açar. Her bilginin yalnızca tek bir yerde saklanması tutarlılığı garanti eder ve bakımı kolaylaştırır.

**Örnek:**
```sql
-- Normalizasyon öncesi (3NF ihlali: SupplierPhone, ProductId'ye değil SupplierName'e bağlıdır)
-- Products(ProductId, ProductName, SupplierName, SupplierPhone)

-- Normalizasyon sonrası (3NF):
CREATE TABLE Suppliers (
    SupplierId INT IDENTITY(1,1) PRIMARY KEY,
    Name       NVARCHAR(100) NOT NULL,
    Phone      NVARCHAR(20)  NOT NULL
);

CREATE TABLE Products (
    ProductId  INT IDENTITY(1,1) PRIMARY KEY,
    Name       NVARCHAR(150) NOT NULL,
    SupplierId INT NOT NULL FOREIGN KEY REFERENCES Suppliers(SupplierId)
);
```

## Index, Execution Plan ve Transaction

### S6. Index nedir? Sorgu performansını nasıl etkiler?

**Index**, tablodaki belirli kolonlara göre sıralı tutulan ve veritabanı motorunun aranan kayıtları tüm tabloyu baştan sona okumadan (**Table Scan**) doğrudan nokta atışı bulmasını (**Index Seek**) sağlayan B-Tree tabanlı bir arama yapısıdır. SQL Server veriyi 8 KB'lık sayfalarda sakladığı için doğru bir index, okunan sayfa sayısını (`logical reads`) binlerden birkaç sayfaya düşürebilir.

Index'ler `WHERE`, `JOIN`, `ORDER BY` ve `GROUP BY` içeren okuma sorgularını büyük ölçüde hızlandırır. Ancak her index verinin ek bir kopyası olduğu için `INSERT`, `UPDATE` ve `DELETE` işlemlerinde ilgili tüm index'lerin de güncellenmesi gerekir; bu da yazma performansında ek maliyet ve fazladan disk alanı tüketimi yaratır. Bu nedenle index'ler rastgele değil, sık çalışan gerçek sorgulara göre planlanmalıdır.

**Örnek:**
```sql
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON Orders (CustomerId);

-- Bu sorgu tüm Orders tablosunu taramak yerine IX_Orders_CustomerId üzerinde Index Seek yapar:
SELECT OrderId, CustomerId
FROM Orders
WHERE CustomerId = 42;
```

### S7. Clustered index ile non-clustered index arasındaki fark nedir?

**Clustered index**, yaprak (leaf) seviyesinde tablonun gerçek veri satırlarını anahtar sırasına göre tutan yapıdır; yani tablonun fiziksel düzeninin bizzat kendisidir. Veri satırları aynı anda yalnızca tek bir kritere göre sıralanabileceğinden bir tabloda en fazla **bir** clustered index bulunabilir (SQL Server'da Primary Key varsayılan olarak clustered oluşturulur).

**Non-clustered index** ise tablodan ayrı tutulan, seçilen kolonlara göre sıralanmış bir fihrist (dizin) gibidir ve bir tabloda birden fazla tanımlanabilir. Yaprak seviyesinde yalnızca index kolonlarının değerleri ve asıl satıra işaret eden clustered key (veya heap tablo ise satır adresi) bulunur. Sorgu index'te olmayan kolonları da istiyorsa SQL Server her satır için ana tabloya giderek **Key Lookup** yapar; bunu önlemek için ek kolonlar `INCLUDE` ile eklenerek **Covering Index** oluşturulur.

**Örnek:**
```sql
-- ProductId zaten Primary Key (Clustered Index) iken Name için Non-Clustered Covering Index:
CREATE NONCLUSTERED INDEX IX_Products_Name
ON Products (Name)
INCLUDE (Price, Stock);

-- Sadece bu index okunur, Key Lookup gerekmez:
SELECT Name, Price, Stock
FROM Products
WHERE Name = N'Mekanik Klavye';
```

### S8. Execution plan ne işe yarar?

**Execution Plan**, SQL Server Query Optimizer'ın bir sorguyu çalıştırmak için ürettiği adım adım yürütme haritasıdır. Tabloların hangi yöntemle okunduğunu (`Table Scan`, `Index Scan`, `Index Seek`), tabloların nasıl birleştirildiğini, `Key Lookup` veya maliyetli `Sort` operatörlerinin oluşup oluşmadığını ve tahmin edilen satır sayısı ile gerçekte okunan satır sayısı arasındaki farkı gösterir.

Performans sorunlarını tahmine dayalı değil kanıtla analiz etmek için kullanılır. SSMS'de `Ctrl+M` (*Include Actual Execution Plan*) ile incelendiğinde eksik index'ler, SARGable olmayan filtreler veya gereksiz veri okumaları açıkça görülür ve yapılan optimizasyonun gerçekten işe yarayıp yaramadığı doğrulanır.

**Örnek:**
```sql
-- SARGable değil -> Execution Plan'da Index Scan (tüm satırlar taranır)
SELECT OrderId, OrderDate FROM Orders
WHERE YEAR(OrderDate) = 2026;

-- SARGable -> Execution Plan'da Index Seek (sadece ilgili aralık okunur)
SELECT OrderId, OrderDate FROM Orders
WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01';
```

### S9. Transaction nedir? COMMIT ve ROLLBACK ne anlama gelir?

**Transaction**, birden fazla veritabanı işlemini "ya hepsi gerçekleşir ya da hiçbiri gerçekleşmez" kuralıyla tek bir mantıksal bütün olarak çalıştıran mekanizmadır. **ACID** (Atomicity, Consistency, Isolation, Durability) prensipleriyle veri tutarlılığını korur; böylece çok adımlı bir süreç yarıda hata aldığında veritabanının bozuk veya eksik durumda kalmasını engeller.

**`COMMIT`**, transaction içindeki tüm değişikliklerin başarıyla tamamlandığını onaylar ve bunları kalıcı hâle getirir. **`ROLLBACK`** ise bir hata veya iş kuralı ihlali oluştuğunda `BEGIN TRAN` anından itibaren yapılmış tüm değişiklikleri geri alarak veritabanını işlem öncesi tutarlı hâline döndürür.

**Örnek:**
```sql
SET XACT_ABORT ON;
BEGIN TRY
    BEGIN TRAN;

    INSERT INTO Orders (CustomerId, Total) VALUES (1, 500.00);
    UPDATE Products SET Stock = Stock - 5 WHERE ProductId = 10; -- CHECK (Stock >= 0) patlarsa CATCH'e düşer

    COMMIT TRAN;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK TRAN;
    THROW;
END CATCH;
```

### S10. Blocking ve deadlock arasındaki fark nedir?

**Blocking**, bir işlemin (session/transaction) erişmek istediği satır, sayfa veya tablo üzerinde başka bir işlemin tuttuğu kilidin serbest kalmasını sırayla beklemesidir. Kilidi tutan işlem `COMMIT` veya `ROLLBACK` yaptığında engel kalkar ve bekleyen işlem kendiliğinden devam eder; dolayısıyla blocking geçici bir performans ve bekleme sorunudur.

**Deadlock** ise iki veya daha fazla işlemin birbirlerinin tuttuğu kilitleri karşılıklı beklemesiyle oluşan ve dış müdahale olmadan asla çözülemeyen döngüsel kilitlenmedir. SQL Server'ın Lock Monitor'ü bu döngüyü tespit ettiğinde işlemlerden birini kurban (*victim*) seçerek geri alır ve uygulamaya `1205` hatası döndürür. Deadlock'u önlemenin temel yolu tablolara ve satırlara her zaman aynı sırayla erişmek ve transaction'ları kısa tutmaktır.

**Örnek:**
```sql
-- Transaction A: Önce Orders (Id = 1), sonra Products (Id = 5) günceller.
-- Transaction B: Önce Products (Id = 5), sonra Orders (Id = 1) günceller.
-- İkisi de ilk kilidi alıp diğerinin kilidini bekler -> DEADLOCK (Hata 1205).

-- Çözüm: Her iki işlem de önce Orders, sonra Products sırasıyla güncelleme yaparsa
-- döngü oluşmaz; en fazla kısa süreli bir BLOCKING yaşanır ve işlem tamamlanır.
```

## EF Core

### S11. ORM nedir? EF Core hangi problemi çözer?

**ORM (Object-Relational Mapper)**, nesne yönelimli programlama dillerindeki sınıflar ve nesneler ile ilişkisel veritabanındaki tablolar ve satırlar arasındaki yapısal farkı otomatik olarak eşleştiren veri erişim katmanıdır.

**EF Core**, geliştiricinin her sorgu için bağlantı açıp kapatma, ham SQL string'leri yazma, `SqlDataReader` ile satırları elle C# nesnelerine dönüştürme ve değişiklik takibi yapma gibi tekrarlayan ve hataya açık işlerini ortadan kaldırır. Tip güvenli LINQ sorguları, otomatik parametreli SQL üretimi, migration ile şema yönetimi ve Unit of Work / Change Tracking desteği sunarak hem geliştirme hızını hem de kod kalitesini artırır.

**Örnek:**
```csharp
// Elle SQL yazıp SqlDataReader map'lemek yerine EF Core ile tip güvenli LINQ:
var expensiveProducts = await db.Products
    .AsNoTracking()
    .Where(p => p.Price > 500m)
    .OrderByDescending(p => p.Price)
    .ToListAsync(ct);
```

### S12. DbContext ve DbSet ne işe yarar?

**`DbContext`**, EF Core'da veritabanıyla yapılan tek bir iş oturumunu temsil eden merkez sınıftır ve **Unit of Work** desenini uygular. Bağlantı yaşam döngüsünü yönetir, LINQ sorgularını SQL'e çevirir, yüklenen entity'lerdeki değişiklikleri Change Tracker ile takip eder ve `SaveChangesAsync()` çağrıldığında biriken değişiklikleri tek bir transaction içinde veritabanına gönderir. Thread-safe olmadığı için Web API'lerde DI container'a `Scoped` olarak kaydedilir.

**`DbSet<TEntity>`** ise `DbContext` içinde belirli bir entity tipine ve veritabanındaki karşılık gelen tabloya açılan kapıdır. İlgili tablo üzerinde LINQ ile sorgulama yapmayı (`Where`, `FirstOrDefaultAsync`) ve değişiklik işlemlerini (`Add`, `Update`, `Remove`) başlatmayı sağlar.

**Örnek:**
```csharp
public class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options)
{
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Product> Products => Set<Product>();
}

// Kullanım:
db.Products.Add(new Product { Name = "Klavye", Price = 1200m, CategoryId = 1 });
await db.SaveChangesAsync(ct);
```

### S13. EF Core migration nedir? Ne zaman kullanılır?

**EF Core Migration**, Code First yaklaşımında C# entity sınıflarında ve Fluent API yapılandırmalarında yapılan model değişikliklerini veritabanı şemasına kontrollü ve adım adım aktaran şema versiyonlama mekanizmasıdır. Her migration, değişikliği uygulayan `Up()` ve geri alan `Down()` metotlarını içeren bir C# sınıfı oluşturur; hangi migration'ların uygulandığı veritabanındaki `__EFMigrationsHistory` tablosunda saklanır.

Veritabanı yapısını uygulama koduyla birlikte kaynak kontrolünde (Git) tutmak ve geliştirme, test, canlı ortamlar arasında veri kaybı olmadan tutarlı şekilde güncellemek gerektiğinde kullanılır. Geliştirme ortamında `dotnet ef database update` ile uygulanırken, canlı ortamda doğrudan `database update` yerine `--idempotent` SQL script üretilip incelenerek çalıştırılması önerilir.

**Örnek:**
```bash
# Model değişikliğinden sonra migration oluşturma
dotnet ef migrations add AddProductSkuIndex

# Geliştirme veritabanına uygulama
dotnet ef database update

# Canlı ortam için güvenli (idempotent) SQL script üretme
dotnet ef migrations script --idempotent -o deploy.sql
```

### S14. Change Tracker nedir? Performansa etkisi nedir?

**Change Tracker**, her `DbContext` örneği içinde bulunan ve takip edilen entity'lerin yaşam durumlarını (`Detached`, `Added`, `Unchanged`, `Modified`, `Deleted`) ve veritabanından okundukları andaki değer kopyalarını (*snapshot*) saklayan bileşendir. `SaveChangesAsync()` çağrıldığında `DetectChanges()` çalışarak mevcut nesne değerlerini snapshot ile kıyaslar ve yalnızca değişen kolonlar için `UPDATE` komutu üretir; ayrıca aynı context içinde aynı primary key için tek nesne döndürerek tutarlılık (*identity resolution*) sağlar.

Performans açısından her takip edilen kayıt için ekstra snapshot ve takip meta verisi tutulması RAM kullanımını ve Garbage Collector yükünü artırır. Context gereksiz yere uzun ömürlü tutulup binlerce nesne biriktirilirse `DetectChanges()` tüm takip edilen nesneleri tarayacağı için CPU kullanımı büyür ve kaydetme işlemleri yavaşlar; bu nedenle `DbContext` kısa ömürlü olmalı ve sadece okuma yapan sorgularda takip kapatılmalıdır.

**Örnek:**
```csharp
var product = await db.Products.FindAsync(10);
product!.Price = 1499.90m;

// Change Tracker yalnızca Price kolonunun değiştiğini tespit eder ve şu SQL'i üretir:
// UPDATE [Products] SET [Price] = @p0 WHERE [Id] = @p1
await db.SaveChangesAsync(ct);
```

### S15. AsNoTracking() hangi durumlarda kullanılmalıdır?

**`AsNoTracking()`**, sorgudan dönen entity'lerin Change Tracker'a eklenmemesini sağlayan EF Core metodudur. Verinin yalnızca okunup gösterileceği, sonrasında değiştirilip `SaveChangesAsync()` ile kaydedilmeyeceği tüm **salt okunur (read-only)** senaryolarda — örneğin GET endpoint'leri, ürün listeleme, arama, sayfalama ve raporlama ekranlarında — kullanılmalıdır.

Snapshot kopyalama ve identity map kontrolü atlandığı için hem bellek tüketimi azalır hem de sorgu sonuçlarının nesneye dönüştürülmesi hızlanır. Ancak `AsNoTracking()` ile çekilen bir nesne üzerinde değişiklik yapılıp `SaveChangesAsync()` çağrılırsa bu değişiklik hata vermeden sessizce yok sayılır; bu nedenle güncelleme yapılacak akışlarda tracking açık bırakılmalıdır.

**Örnek:**
```csharp
var products = await db.Products
    .AsNoTracking()
    .Where(p => p.CategoryId == categoryId)
    .OrderBy(p => p.Name)
    .ToListAsync(ct);
```

## EF Core Performans ve Security

### S16. N+1 sorgu problemi nedir? Nasıl önlenir?

**N+1 sorgu problemi**, önce ana listeyi çekmek için **1** sorgu çalıştırıldıktan sonra, gelen **N** adet kaydın her biri için ilişkili veriyi getirmek üzere veritabanına döngü içinde (veya fark edilmeden Lazy Loading aracılığıyla) **N** adet ek sorgu gönderilmesidir. Örneğin 100 kategorinin ürünlerini listelerken toplam 101 SQL sorgusu atılır; her sorgu ayrı bir ağ gidiş-dönüş (round-trip) maliyeti oluşturduğu için gerçek veride ciddi gecikmelere yol açar.

Bu problemi önlemek için ilişkili veriler tek sorguda yalnızca gerekli alanları çeken **DTO Projection (`Select`)** ile veya **Eager Loading (`Include` / `ThenInclude`)** kullanılarak yüklenmelidir. Aynı seviyede birden fazla koleksiyon `Include` edildiğinde oluşabilecek kartezyen patlama (Cartesian Explosion) durumunda ise `AsSplitQuery()` ile sorgu sabit sayıda parçaya bölünür; ayrıca Lazy Loading kapalı tutulmalı ve geliştirme ortamında üretilen SQL logları düzenli kontrol edilmelidir.

**Örnek:**
```csharp
// YANLIŞ (N+1): 1 sorgu kategoriler için + N sorgu her kategorinin ürünleri için
var categories = await db.Categories.ToListAsync(ct);
foreach (var c in categories)
{
    var products = await db.Products.Where(p => p.CategoryId == c.Id).ToListAsync(ct);
}

// DOĞRU (Tek sorgu - Eager Loading):
var categoriesWithProducts = await db.Categories
    .AsNoTracking()
    .Include(c => c.Products)
    .ToListAsync(ct);
```

### S17. Projection neden Include kullanımından daha performanslı olabilir?

`Include`, ana tablonun ve ilişkili tabloların **tüm kolonlarını** (uzun açıklamalar, kullanılmayan metinler veya audit alanları dahil) veritabanından çeker, ağ üzerinden taşır ve ilişkili entity'lerle birlikte bellekte tam nesne grafiği oluşturur. Birden fazla koleksiyon dahil edildiğinde JOIN nedeniyle tekrar eden satır sayısı katlanarak büyüyebilir.

**Projection** (`Select` ile bir DTO veya anonim tipe eşleme) ise SQL'de yalnızca gerçekten ihtiyaç duyulan kolonların seçilmesini sağlar, `Count()` / `Sum()` gibi hesaplamaları veritabanı tarafında yaptırır ve gereksiz kolonların taşınmasını engeller. Üstelik DTO'lar Change Tracker tarafından izlenmez ve daha az kolon istendiği için SQL Server'ın **covering index** kullanma ihtimali artar; sonuç olarak veritabanı I/O'su, ağ trafiği ve RAM tüketimi ciddi biçimde düşer.

**Örnek:**
```csharp
// Include tüm Product ve Category kolonlarını çekerken,
// Projection yalnızca 4 kolonu SELECT eder ve tracking maliyeti oluşturmaz:
var list = await db.Products
    .Where(p => p.Stock > 0)
    .Select(p => new ProductListDto(p.Id, p.Name, p.Price, p.Category.Name))
    .ToListAsync(ct);
```

### S18. IQueryable ile IEnumerable arasındaki kritik fark nedir?

Kritik fark, `Where`, `OrderBy`, `Skip`, `Take` ve `Select` gibi LINQ işlemlerinin **nerede çalıştırıldığıdır**. `IQueryable<T>`, bu işlemleri ifade ağacı (`Expression Tree`) olarak biriktirir ve sorgu çalıştırıldığında (`ToListAsync`, `CountAsync`, `FirstOrDefaultAsync` vb.) SQL'e dönüştürerek doğrudan **veritabanında** yürütür.

`IEnumerable<T>` ise bellek içi koleksiyonlar üzerinde C# delegeleriyle çalışır. Bir EF Core sorgusunda filtrelemeden önce `ToList()` çağırmak veya bir metodun dönüş tipini `IEnumerable<T>` yapmak, tablonun tamamının filtresiz biçimde uygulamanın RAM'ine çekilmesine ve filtrelemenin bellekte satır satır yapılmasına yol açar. Bu durum veritabanı index'lerinin kullanılmasını engeller ve büyük tablolarda ciddi bellek/performans krizine sebep olur.

**Örnek:**
```csharp
// YANLIŞ (IEnumerable): Tüm Orders tablosunu RAM'e çeker, sonra C# içinde filtreler.
var wrong = db.Orders.ToList().Where(o => o.City == "İzmir").ToList();

// DOĞRU (IQueryable): WHERE [City] = N'İzmir' SQL'ini veritabanında çalıştırır.
var correct = await db.Orders
    .AsNoTracking()
    .Where(o => o.City == "İzmir")
    .ToListAsync(ct);
```

### S19. SQL Injection nedir? EF Core veya Dapper kullanırken nasıl önlenir?

**SQL Injection**, kullanıcıdan gelen girdinin SQL sorgu metnine doğrudan string birleştirmeyle eklenmesi sonucu, verinin SQL komutu olarak yorumlanıp çalıştırılmasıyla ortaya çıkan kritik bir güvenlik açığıdır. Saldırgan bu yolla kimlik doğrulamayı atlayabilir (`' OR 1=1 --`), başka tablolardaki hassas verileri çekebilir (`UNION SELECT`) veya veritabanındaki verileri değiştirip silebilir.

Kalıcı çözüm **Parameterized Query (parametreli sorgu)** kullanmaktır; böylece SQL komutu ile kullanıcı girdisi veritabanına ayrı ayrı iletilir ve girdi asla çalıştırılabilir kod olarak değerlendirilmez. EF Core'da standart LINQ sorguları zaten otomatik parametrelidir; ham SQL gerektiğinde `FromSqlRaw($"... '{input}'")` yerine `FormattableString` alan `FromSql($"... = {input}")` veya parametreli `FromSqlRaw("... = {0}", input)` kullanılmalıdır. Dapper'da ise `@Param` yer tutucusu ile değerler anonim nesne üzerinden gönderilmeli; parametre olamayan dinamik kolon/sıralama adları için ise mutlaka **whitelist (beyaz liste)** kullanılmalıdır.

**Örnek:**
```csharp
// EF Core güvenli kullanım (otomatik @p0 parametresi üretir):
var productsEf = await db.Products
    .FromSql($"SELECT * FROM Products WHERE Name = {searchTerm}")
    .ToListAsync(ct);

// Dapper güvenli kullanım (parametreli):
var productsDapper = await connection.QueryAsync<Product>(
    "SELECT * FROM Products WHERE Name = @SearchTerm",
    new { SearchTerm = searchTerm });
```

### S20. Connection string güvenliği ve least privilege DB user yaklaşımı neden önemlidir?

**Connection string**, uygulamanın veritabanına erişmek için kullandığı sunucu ve kimlik bilgilerini içerir. Bu bilgilerin `appsettings.json` gibi kaynak kod dosyalarına yazılması, Git geçmişine girerek ekip içi yetkisiz kişilere veya yanlışlıkla açık yapılan depolarda tüm internete sızması riskini doğurur. Bu nedenle geliştirme ortamında **User Secrets**, canlı ortamda ise **Environment Variables**, Key Vault / Secret Manager veya Managed Identity kullanılmalıdır.

**Least Privilege (En Az Yetki)** ilkesi ise bir şifre sızsa veya uygulamada bir SQL Injection açığı oluşsa dahi zararı sınırlamak için kritik önemdedir. Uygulama hiçbir zaman `sa` veya `db_owner` gibi tam yetkili hesaplarla bağlanmamalı; yalnızca işini yapması için gerekli veri erişim yetkilerine (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) sahip kısıtlı bir veritabanı kullanıcısı kullanmalıdır. Tablo oluşturma veya silme gibi şema değişiklikleri (`DDL` / migration) deploy sırasında ayrı ve geçici/kontrollü bir yetkili hesapla yürütülmelidir.

**Örnek:**
```bash
# Geliştirme ortamında şifreyi Git dışındaki User Secrets'a kaydetme:
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=localhost;Database=MiniShopDb;User Id=minishop_app;Password=GucluSifre!;Encrypt=True"
```
```sql
-- SQL Server'da yalnızca veri okuma/yazma yetkisi olan (DROP TABLE yapamayan) kullanıcı:
CREATE LOGIN minishop_app WITH PASSWORD = 'GucluSifre!';
USE MiniShopDb;
CREATE USER minishop_app FOR LOGIN minishop_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::dbo TO minishop_app;
```
